가공 시간 계측 설계

작업자와 검수자가 실제로 쓴 시간을 어떻게 잴 것인가. CVAT가 이미 수집 중인 이벤트만으로 목표 테이블을 채울 수 있다.

핵심: 두 개의 시계를 섞지 않는다

같은 job에 대해 두 값이 5~10배 차이 난다. 어느 쪽을 쓰느냐가 결론을 바꾼다.

실작업 시간 · effort

send:working_time

연속된 사용자 액션 사이의 간격을 더하되, 100초를 넘는 간격은 버린다. 자리비움·야간·검수 대기가 자동으로 빠진다. job 단위로 이미 쪼개져 있다.

벽시계 시간 · leadtime

update:job 전이 간격

착수부터 최종 승인까지 흐른 실제 시간. 검수 대기와 야간·주말을 포함한다. 프로젝트가 언제 끝나는지는 이 시계로만 답할 수 있다.

실측 결과 벽시계 중 실작업 비율은 9~18%였다. 나머지 82~91%는 검수 대기, 야간, 자리비움이다. 그래서 지표를 이렇게 나눈다.

모델 효과(p) 추정 → effort. 가속 효과만 보려면 대기 시간이 섞이면 안 된다.

project 완료 시간 → leadtime. 검수 왕복이 직렬화되는 비용이 이 지표의 본질이다.

로그인/로그아웃 시각만으로는 부족하다. 자리비움 1회당 최대 10분씩 오차가 누적되고, 로그인 세션 길이로는 job별 시간을 나눌 수 없다. 다만 로그인 기록은 컴플라이언스 증거로서 가치가 있다 — 세션 길이 대비 실작업 비율이 낮으면 "로그인만 해두고 자리를 비웠다"가 데이터로 남는다.

워크플로와 이를 표시하는 이벤트

프로덕션 project 147의 실제 전이를 그대로 옮긴 것이다. 모든 전이는 update:job으로 기록되며, 행위자가 user_name에 정확히 남는다.

job 하나를 찍으면 나오는 것

job_id 하나만 넣으면 라운드별로 가공·검수·재가공·재검수가 분리된다. 구간은 위 전이로 자르고, 그 구간에 떨어지는 실작업 시간을 작업자와 검수자로 나눠 합산한다.

목표 테이블의 각 칸을 무엇으로 채우는가

전부 기존 이벤트에서 나온다. 새로 심을 계측은 없다.

목표 칸계산출처 이벤트
단일 Job 완료 시간작업자 effort + 검수자 effortsend:working_time
단일 검수 완료 시간검수자 effort 평균send:working_time
최초 Job 완료 시간가장 먼저 승인된 job 1건+ update:job
모든 Job 완료 시간작업자별 effort 합계send:working_time
project 완료 시간max(승인) − min(착수)update:job
task 1 대비 단축율(T₁ − Tₓ) ÷ T₁위 값에서 파생

역할은 자동 판별한다 — stage → acceptance 전이를 수행한 사람이 검수자, job별 실작업이 가장 많은 비검수자가 작업자.

job 진입 시점의 state·stage도 필요하면 복원할 수 있다. load:job에는 담겨 있지 않지만, create:job의 초기값에서 시작해 전이 이력을 as-of 조회하면 나온다. 소급 적용되므로 과거 데이터에도 그대로 쓸 수 있다.

실험 전에 통제할 것

10분 로그아웃 규칙보다 이쪽이 측정 정확도에 훨씬 크게 작용한다.

  1. 탭 하나만 사용두 탭에서 서로 다른 job을 동시에 열면 이벤트 스트림이 섞여 job 귀속이 틀어진다. 지금 설계에서 가장 큰 실제 위험이다.
  2. 계정 공유 금지실작업 시간은 user_id로 집계된다. 한 계정을 둘이 쓰면 분리가 불가능하다.
  3. 실험 직전 파이프라인 재확인덤프로 확인된 것은 2026-08-24까지다. 그 이후 vector → ClickHouse 구간이 끊겼을 가능성은 배제할 수 없다. 시작 전날 send:working_time의 last_seen을 한 번 본다.
  4. 로그아웃은 버튼을 눌러야 기록된다토큰 인증이라 탭만 닫으면 logout:user가 남지 않는다. 짝이 없는 로그인은 그 자체로 미준수 신호이므로, 이 동작을 그대로 두고 해석에 쓴다.

실행

쿼리 세트는 docs/analytics/annotation-time-metrics.sql에 있다. 파라미터는 project id 또는 job id 하나뿐이다.

# 0번 섹션(뷰 생성)을 한 번 실행한 뒤, 1·2번을 task마다 반복
docker exec cvat_clickhouse_everex clickhouse-client \
  --user user --password user \
  --param_proj=<project_id> --query "<쿼리>"

실험의 task 1/2/3은 CVAT project 3개에 대응한다. 각 project id로 1번과 2번 쿼리를 돌리면 목표 테이블 두 개가 그대로 채워진다. 단축율은 세 결과를 받아 계산한다.

개별 job을 파고들 때는 3b번 섹션의 뷰를 쓴다. --param_job=<job_id> 하나면 된다.

docker exec cvat_clickhouse_everex clickhouse-client \
  --user user --password user --param_job=74137 \
  --query "SELECT * FROM cvat.job_rounds(job = {job:UInt64})"
